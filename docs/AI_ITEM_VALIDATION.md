# AI_ITEM_VALIDATION — AI 아이템 3관문 체크 + 단위경제 10건 테스트 (초안)

**상태: 3관문 체크는 코드/문서 근거로 답변 완료(§1). 10건 테스트는 실제 발화 데이터가
없어 미실행(§2) — 사용자 확인 필요.**
2026-09-12, 포항 테크노파크 바이브코딩 교안 3일차(AI 창업 아이템 발굴 워크숍) 근거.

## 1. AI 아이템 3관문 체크

핵심 AI 판단 대상: 요양보호사 자유발화 → 관찰 도메인별 상태(`same_as_usual`/`changed`/
`not_observed`/`uncertain`) 분류 + 부족한 정보에 대한 추가질문 생성 + 구조화 보고문 작성.

### ①규칙으로 못 적는 판단인가?

**부분적으로만 그렇다 — 이미 실제로 규칙 기반 부분과 AI 부분이 나뉘어 있다.**
[shared/noChangeEngine.ts](../shared/noChangeEngine.ts)를 보면 "특이사항 없음" 계열 문구
감지와 도메인 키워드 매칭(식사/수분/이동/낙상 등)은 **이미 순수 규칙 기반**으로 동작한다
(코드 주석: "Gemini 키 없이도, 서버 왕복 없이도 항상 동작한다"). AI가 실제로 필요한
부분은 이 규칙에 걸리지 않는 **자유롭고 모호한 발화**(예: "오늘 좀 이상하셨어요" 같은
비정형 표현)를 해석하고, 어떤 후속 질문이 지금 상황에 자연스러운지 판단하고, 여러
문장을 하나의 일관된 보고문으로 종합하는 부분이다. 즉 "AI가 꼭 필요한 판단"은 전체가
아니라 **규칙 매칭 밖의 나머지 영역**으로 이미 좁혀져 있다 — 이 자체가 3일차 원칙("AI
설계 4패턴" 중 "분류하고 넘기기": 규칙이 되는 건 규칙에, AI가 필요한 것만 AI에)과
일치한다.

### ②틀려도 되게 설계 가능한가(사람 최종확인 지점이 있는가)?

**있다 — 이중으로 있다.** (1) 요양보호사 본인이 AI 초안을 확인·수정 후 제출한다
(`caregiver_final_report`가 `ai_generated_report`와 다를 수 있음 — `aiDraftEditRate`로
이미 계측 중). (2) 관리자가 제출된 기록을 다시 검토(승인/반려)한다. 응급 신호는 AI
판단과 별개로 규칙 기반 감지(`shared/emergency.ts`)가 항상 자동 제출 없이 사람에게
확인 화면을 띄운다. 다만 [docs/METRIC_HYPOTHESES.md](METRIC_HYPOTHESES.md) §2(H2)에서
짚었듯, "틀려도 사람이 잡아준다"가 실제로 작동하는지는 `inaccuracyRate`(관리자가 실제
오류를 발견한 비율)로만 검증되며, 이 값이 아직 충분히 쌓이지 않았다면 이 게이트를
"통과"로 확정할 수 없다 — 검증 필요.

### ③다음 세대 AI 모델이 이 판단을 그냥 대체하면 뭘로 버티는가?

**아직 뚜렷한 답이 없다 — 이번 3관문 체크에서 가장 취약한 지점.** 현재 코드/문서에서
확인 가능한 후보:
- **현장 워크플로우 데이터**: 참여자 코드(C01~C09)-수급자 배정, 반복 보고 이력, 관리자
  검토 이력 등은 시간이 지날수록 이 서비스 안에 쌓인다(전환 비용).
- **기관 관계·신뢰**: 가드림365재가복지센터 등 실제 현장에서 이미 쓰고 있다는 사실
  자체.
- 하지만 이 둘 다 "다음 세대 범용 AI가 같은 UI를 베끼면 못 버티는" 방어막은 아니다 —
  둘 다 [검증 필요]이며, 임의로 강한 답을 만들어내지 않는다. 이 질문은 코드로 답할 수
  없는 사업 판단이라 사용자 결정이 필요하다.

**요약**: ①②는 현재 설계로 이미 통과에 가깝다(근거 있음). ③은 미해결 — 사업 방향
결정이 필요한 지점이다.

## 2. 단위경제 10건 테스트 — 실행 전 확인 필요

교안 제안: 실제 요양보호사 발화 샘플 10건을 정해 AI 결과 합격/불합격을 수동 채점해,
"정확도 92%" 같은 숫자를 쓰기 전에 정의와 근거를 먼저 갖춘다.

**이 저장소 안에서 실행하지 않은 이유**: 실제 요양보호사 발화 로그는 운영 데이터(개인
정보 포함 가능)이고, 이 개발 환경에는 Supabase 자격증명이 없어 직접 조회할 수 없다
(AGENTS.md §4). `docs/METRIC_HYPOTHESES.md`와 마찬가지로 임의 수치를 만들지 않는다는
원칙상, 실제 로그 없이 "10건 중 O건 합격"을 지어낼 수 없다.

**제안하는 진행 방법(선택):**
1. 사용자가 실제 운영 DB(Supabase)에서 최근 발화 원문(`raw_input`) 10건을 익명화해
   내려받아 공유 — 이 경로로 하면 실제 수치를 낼 수 있다.
2. 또는 `shared/statsCalc.ts`의 `STANDARD_SCENARIOS`(표준상황 연습, 이미 코드에 있는
   2개 시나리오)로 먼저 10건 규모 연습을 만들어 스코어링 기준을 시험해보고, 실제 로그가
   쌓이면 같은 기준으로 교체 — 이 경로는 지금 당장 코드 변경 없이 시작할 수 있지만,
   결과는 "실제 발화 정확도"가 아니라 "연습 시나리오 통과율"임을 반드시 구분해서 표시
   해야 한다(이미 `expertAppropriatenessStatus: 'not_evaluated'`로 관련 원칙이 코드에
   있음).
3. 채점 기준("합격"의 정의) 자체도 사용자가 먼저 확정해야 한다 — 예: "필수 4항목
   (change/action/result/escalation) 중 몇 개가 확보돼야 합격인가", "금지어(허위 사실)
   가 하나라도 나오면 즉시 불합격"처럼.

## 3. 변경 이력

  statsCalc.ts)와 AGENTS.md만 근거로 답변. 10건 테스트는 실제 데이터 부재로 미실행.
