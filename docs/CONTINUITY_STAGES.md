## 2. 1단계 구현 내용

PSST 대응: "매일 기록을 직접 대조해야 하는 부담" → 관리자가 **어떤 수급자의 무엇을 왜** 봐야 하는지 찾고,
그 수급자의 과거 보고를 한 흐름에서 본다. 새 AI·문서 처리·조치 기능은 넣지 않았다.

- **기관 범위(서버 권한)**: 관리자 세션 JWT에 기관 ID(`orgId`)를 담는다. 모든 관리자 데이터 API(reports·stats·
  export·participants·recipients)는 `requireAdminOrganization`으로 세션 기관을 확인하고, 요청의 `org` 쿼리가 세션
  기관과 다르면 403이다. 기관 클레임이 없는 기존 세션은 이 배포의 기관으로 읽는다(재로그인 강제 없음). 기관 정의:
  `shared/organization.ts` — 이 배포는 기관 한 곳(가드림365재가복지센터, `gadream365`)의 데이터만 담는다.
  다기관 가입·과금·최고관리자는 만들지 않았다.
- **수급자 허브 API**: `GET /api/admin/recipients?org=` (수급자 목록 + 검토 대기 목록),
  `GET /api/admin/recipients?org=&code=&period=7|30|all` (수급자 타임라인). 읽기 전용(감사 로그만 기록).
  표준상황 연습·삭제 보고 제외. 계산은 `shared/recipientHub.ts`(서버·데모 공통).
- **화면**: `/admin`(기관 첫 화면에 "검토할 보고와 이유" 목록 — 기존 숫자 타일·연구 지표 유지),
  `/admin/org/:org/recipients`(수급자 목록), `/admin/org/:org/recipients/:code`(상단 요약 + 기간 선택 + 보고
  타임라인), `/admin/reports/:id`(기존 보고 상세·승인/반려). 화면 상태를 주소에 담아 새로고침·직접 URL·뒤로가기가
  동작한다. `?demo=1`은 이동 시 유지된다.
- **타임라인 한 건**: 제출 시각·보고일·작성자(요양보호사 코드)·검토상태 → 확인할 이유(검토 대기일 때) → 항목별
  상태(저장된 값만) → ① 보고 원문(보고자 진술)과 추가 질문·답변 ② 구조화 기록(요양보호사 확인본, AI/규칙 초안은
  접어서) ③ 관리자 검토(상태·처리 시각·첫 열람·검토본·메모 공개 여부·이력 수) → "원본 보고 열기 · 승인/반려".
- **검토 대기 이유**(저장된 값만): 승인·반려 기록 없음 / 응급 표현 감지(규칙 기반) / 저장된 변화 보고 항목 /
  요양보호사 초기 선택(평소와 다름·확인 필요·평소와 비슷함) / 저장된 미관찰·불확실 항목 / 요양보호사 본인 지원
  요청(어르신 상태와 별개) / AI 대체 처리 / 관찰 정보 없는 보고. 정렬은 응급 표현 표시 → 제출 오래된 순이며
  위험도 점수가 아니다.
- **상태 표시 원칙**: 항목별 상태는 `평소와 같음/변화 보고/미관찰/불확실`만 저장값 그대로 보인다. 저장 안 된 항목은
  보이지 않고, 보고에 저장값이 없으면 "저장되지 않았습니다 — 정상·이상으로 해석하지 않습니다"라고 쓴다.
  **"미응답"은 항목별로 저장되는 값이 없어 표시하지 않는다**(질문하지 않은 항목을 미응답으로 세지 않음).
  보고 전체 상태(승인/반려)로 항목 상태를 대신하지 않는다.
- **DB 변경 없음**(마이그레이션 없음). 운영 DB에 적용할 것이 없다.

## 3. 2단계 전 확인 사항 (사용자 요청, 1단계 중 확인한 범위 — 코드 기준, 운영 DB 값은 확인 불가)

그 문서는 2단계부터 단계별로 적용하며, 1단계에서는 실행하지 않았다.

  "미응답" 값은 없다. **세부 영역 키**: `meal`, `hydration`, `mobility`, `fall`, `excretion`, `cognition_communication`,
  `emotion_behavior`, `pain_breathing`, `sleep`, `skin_hygiene`, `medication`, `other`, `not_checked` + 과거 기록 전용
  `meal_hydration`, `mobility_fall`. 저장 위치는 `reports`의 `observed_/changed_/unobserved_/uncertain_domains_json`
  4개 JSON 컬럼. 서버(`api/care/reports.ts`)는 받으면 저장하지만 현재 현장 화면은 이 값을 보내지 않는다(§1).
  분류는 원문 키워드 규칙(`shared/noChangeEngine.ts` `classifyDomainsFromText`)이며 요양보호사가 항목을 직접 고른 값이 아니다.

  제출 전 초안에도 즉시 저장된다. 현장은 119/센터 전화 안내 화면으로 분기한다. 관리자 쪽은 🔴 배지와 "우선 확인

  같은 필드). 1단계는 이 구조를 바꾸지 않고 검토 대기 목록의 정렬·이유 표시에만 썼다.

### 규칙 요약

- 판단은 제출된 보고에만. 조치 필요 판단은 조치와 별도로 남는다(조치 연결률 분모). 정상 보고는 판단만으로 끝낸다.

- "다음 실제 방문"은 날짜를 만들지 않는다(DB 제약으로도 막음). 관리자 기한에는 쓸 수 없다.
- 기한 변경은 이유 필수, 최초 기한은 그대로. 완료 후 새 확인이 필요하면 "재개"로 새 주기를 만든다(이전 완료·기한 보존).
- 현장 확인 요청은 현장 답변 확인 전에는 완료할 수 없다(취소만). 관리자 직접 조치는 실제 수행 사실·결과 근거를 적어 완료한다.
- 안전 검토는 보고 승인과 별개. 보고를 승인해도 안전 신호는 "미검토"로 남는다. 검토 완료는 대상자 안전 보장이 아니다.
- 제출 전 임시저장의 신호는 서버에 저장된 것만 따로 보이고 제출 지표에서 뺀다. 이 기능 이전에 승인/반려만 된 신호는 "검토 여부 불명확"으로 따로 센다.

### 규칙 요약

- **읽음·응답·결과 확인·완료 구분**: 게시 → 현장 화면 첫 표시(화면에 실제로 보였을 때만 기록 — 게시만으로 읽음을 추정하지
  않음) → 응답 도착(현장 응답 대기 해소, 조치는 진행 중, 관리자 재확인 의무 남음) → 관리자 결과 확인(요약·근거·시각) →
  종결 또는 추가 확인(새 주기).
- **현장에 보이는 것**: 게시 중인 요청의 문구와 응답기한만. 내부 메모·판단·담당 입력값은 현장 API가 읽지도 내려주지도 않는다.
- **대상**: 현재 배정 담당(배정이 바뀌면 새 담당에게 보임) 또는 지정 요양보호사(지금 배정된 사람 중에서만). 배정이 바뀌어
  누구에게도 보이지 않으면 "재배정 필요"로 뜬다. 배정이 없으면 게시할 수 없다.
- **응답**: 보고 제출과 함께 저장한다(보고가 먼저 저장되고 답이 그 보고 id에 연결). 기본값은 "이번에는 답하지 않음".
  이번 보고 원문에서 요청과 같은 돌봄 영역을 말한 문장을 찾아 "이 내용으로 답하기"로 한 번 눌러 확인만 받는다 — 다시
  묻지 않고, 자동으로 응답 처리하지 않는다. 서버는 근거 문장이 그 보고에 저장된 원문에 실제로 있을 때만 원문 근거로
  저장한다. 답한 요청은 현장에 다시 뜨지 않는다. 답 저장이 실패하면 보고는 저장된 채 재시도 안내가 나오고, 재시도해도
  보고는 한 번만 저장된다.
- **철회**: 요청을 내리고 현장 응답 의무를 게시 전으로 되돌린다(기한 유지) — 문구를 고쳐 같은 주기에 다시 게시할 수 있다.
  조치 취소·결과 확인은 게시 중인 요청을 함께 내린다. 그 뒤 도착한 답은 "늦은 응답"으로 기록만 남고 요청·조치를 되살리지 않는다.
- **결과 확인**: 확인 불가·거절·연락 불가·외부 인계는 남은 문제와 다음 책임이 필수. 결과는 사실 기록이며 "나아진 것으로
  확인"도 건강 개선 지표로 집계하지 않는다(이번 단계에는 결과 집계가 없다). 추가 확인은 새 주기·새 기한(과거 기한·응답·확인
  기록 보존), 재개방도 새 주기(현장 응답기한 포함).
- **미응답**: "미응답 실패" 상태를 만들지 않는다. 대기 상태는 저장된 사실로만 나눈다 — 현장 응답기한 지남 / 게시 뒤 이
  수급자 보고는 있었지만 이 요청에는 답 없음 / 방문 대기(다음 방문 자료 없음) / 응답 대기.
- **동시성**: 관리자가 화면을 연 사이 응답이 오면 조치 버전이 올라가 관리자 저장은 충돌로 막히고 입력은 유지된다. 요청 버전
  대조로 응답과 철회가 겹쳐도 한쪽만 반영된다.

  원문 근거 문장으로 한 번에 답하게 했다. 근거 문장 찾기는 키워드 규칙(`classifyDomainsFromText`)이라 못 찾을 수 있다 — 그때는
  답 종류를 직접 고른다.
- 방문 일정 자료가 없어 "다음 실제 방문"이 지났는지 판단하지 않는다.
- 배정 변경 이력 테이블은 없다 — 게시·대상 변경 이벤트에 당시 배정 목록을 남긴다.
- 운영 DB에서의 연결(요청→응답→재확인→완료)은 PGlite(실제 Postgres)로 같은 마이그레이션을 돌려 검증했다. 운영 Supabase에는
  이 환경에서 접근할 수 없어 적용·확인하지 못했다.

### DB 적용 절차(사용자 작업 — 이 환경에는 Supabase 접근 권한이 없음)

1. 2단계를 아직 적용하지 않았다면 `db/migrations/2026-09-15-admin-workflow.sql`부터 적용한다(§5).
2. SQL Editor → `db/migrations/2026-09-16-field-requests.sql` 전체 붙여넣기 → Run. 2단계가 없으면 이 파일은 첫 줄에서 멈추고
   아무것도 바꾸지 않는다. 여러 번 실행해도 안전하다.
3. 같은 파일 머리말의 확인 쿼리로 5개 값이 모두 true인지 본다.
4. 관리자 화면을 새로고침하면 새 카드의 "준비 중"이 사라지고 게시·결과 확인이 켜진다(앱 재배포 불필요).

## 7. 4단계 — 기준문서 원본 · 관리자 확인 기준정보 · 조치 근거 (2026-09-15)

PSST 대응: "관리자 판단에 기준과 출처가 부족함" → 수급자별 원본 문서를 비공개로 보관하고, 관리자가 원본을 보며
입력·확인한 기준정보를 관찰 표시와 조치의 근거로 이어 준다. 기준정보는 **선택 사항**이다 — 없어도 조치·현장 요청은 그대로 쓴다.

### 착수 시 확인

| 항목 | 판정 | 근거 |
|---|---|---|
| 기존 업로드·스토리지 | **없음** | 모든 브랜치 검색: 서버 업로드·Supabase Storage 사용 코드 없음. 유일한 파일 입력은 안전 스캐너(`src/safetyScanner`)의 사진 단계로, 브라우저 세션 미리보기만 하고 서버에 저장하지 않는다 |
| 기존 자동 추출(OCR·LLM) | 없음 | — 새로 만들지 않았다(필수 요건 아님) |
| 항목별 관찰 태그의 근거 | 없음 | `DomainEntry`는 `{domain, status}`뿐 — 항목별 근거 문장이 저장된 적이 없다 |

그래서 "기존 업로드 재사용"은 할 수 없었다. 대신 **이미 쓰는 Supabase 프로젝트와 서버 클라이언트**(`@supabase/supabase-js`,
Service Role)로 비공개 저장소 버킷을 쓰고, 새 라이브러리·새 외부 서비스는 넣지 않았다. 브라우저는 Supabase에 직접 접근하지 않고
관리자 API가 파일을 받아 검사한 뒤 저장한다.

### 데이터(추가형 마이그레이션 `db/migrations/2026-09-17-source-documents.sql` — 2단계 → 3단계 → 이 파일 순서)

| 테이블/저장소 | 성격 | 핵심 |
|---|---|---|
| 버킷 `care-source-documents` | 비공개(공개 버킷이면 앱이 쓰지 않음), PDF·JPG·PNG, 4MB | 원본 파일. 경로 = 기관/수급자/요청 식별자 |
| `source_documents` | 원본·메타데이터 불변, 삭제 불가, 철회만(되돌림 불가) | 문서유형(급여제공계획서·개인별 장기요양이용계획서·낙상/욕창/인지 평가·기타)·제목·**문서 기준일(모르면 null)**·출처·원래 파일명·형식·크기·SHA-256·업로드 시각·올린 범위(기관 공유 계정)·입력한 확인자·교체한 이전 문서·철회 이유 |
| `baseline_entries` | 내용 불변, 수정 = 새 버전 행(같은 묶음·버전 유일) | 종류(관찰·평가 결과 / 계획·목표 / 정식 척도 결과 / 관리자 판단·메모)·세부 영역·설명·값·단위·척도 도구·버전·기준일(척도는 측정일)·유효기간·근거(문서+쪽·발췌 / 관리자 입력+출처 메모)·상태(미확인 초안 / 관리자 확인 / 철회)·이전 버전 표시 |
| `baseline_reference_choices` | 추가만 | 상충하는 값 중 관리자가 고른 현재 참고값과 이유 |
| `action_baseline_links` | 삭제 불가, 해제는 한 번 기록 | 조치 ↔ **연결 당시 기준정보 버전 행**(+ 당시 근거 문서). 연결·해제는 조치 이력(`baseline_linked`/`baseline_unlinked`)에도 남는다 |

쓰기는 DB 함수 `baseline_apply` 하나가 잠금 → 같은 요청 재전송이면 "중복" → 버전·최신 여부·같은 기관/수급자·철회 문서 금지를
다시 확인하고 한 트랜잭션에 쓴다. 정식 척도 필수 항목, 문서 근거 = 문서 id, 빈 항목 금지도 DB 제약으로 막는다.
규칙은 `shared/baseline.ts`(서버·데모 공통).

### 규칙 요약

- **원본 올리기**: 파일 앞부분(매직 바이트)으로 형식을 판정한다(확장자·브라우저 형식은 믿지 않음). 4MB 초과·빈 파일·다른 형식 거부.
  브라우저가 계산한 SHA-256과 서버가 받은 파일의 값이 다르면 거부(전송 중 손상). 순서는 "파일 저장 → 기록 저장"이고, 기록
  저장이 실패하면 방금 올린 파일을 지운다(기록이 실제로 없을 때만). 같은 요청 식별자로 재시도하면 같은 경로에 덮어써 한 벌만 남는다
  — 기록이 없는 파일을 가리키는 일은 없다.
- **원본 보기**: 관리자 세션으로만, 캐시 금지. 철회된 문서도 과거 근거 확인을 위해 열 수 있다.
- **기준일**: 모르면 비워 둔다. 업로드일로 대신하지 않는다. 문서 기준일을 기준정보의 기준일로 쓰려면 관리자가 명시적으로 누른다.
- **입력과 확인**: 입력하면 "미확인 초안" — 판단 근거·조치 연결에 쓰이지 않는다. "관리자 확인"을 거쳐야 유효. 수정은 새 버전
  (새 버전이 확인되면 이전 버전은 "이전 버전"으로 남음). 잘못 입력한 값은 이유와 함께 철회(기록은 남음).
- **계획과 관찰 구분**: 계획·목표는 "관찰 결과 아님"으로 따로 보인다. 일일 보고를 기준정보로 자동으로 올리지 않는다.
  문서 기록은 보고 타임라인·보고 지표에 섞지 않는다.
- **정식 척도**: 도구명·버전·측정값·단위·측정일·출처(문서 또는 출처 메모)가 모두 있을 때만. 계산·환산·건강점수 없음.
- **문서 외 출처**: "관리자 입력 — 공식 평가 결과 아님"으로 표시.
- **상충**: 같은 수급자·종류·세부 영역(·척도 도구)에 출처가 다른 확인 값이 여럿이면 모두 보존하고 "현재 참고값 확인 필요"로
  보인다. 관리자가 이유와 함께 고른다. 고른 뒤 새로 확인된 다른 값이 생기면 다시 확인 필요로 돌아간다(최신 업로드로 자동 대체 없음).
- **조치 근거**: 초안·진행 중 조치에 관리자 확인된 현재 버전만 연결. 연결은 그 버전 행을 가리키므로 기준정보가 고쳐지거나 문서가
  교체·철회돼도 "판단 당시 v1"과 "이후 v2" "근거 문서 이후 철회됨"이 함께 보인다. 모든 조치에 강제하지 않는다.
- **과거 항목 태그**: 저장된 태그에는 항목별 근거가 없으므로 "항목별 근거 연결 전 — 보고 전체를 근거로 함"으로 표시하고, 태그를
  누르면 보고 전체가 열린다. 문장 근거를 만들어 붙이지 않는다. 확인된 기준정보가 있는 영역이면 "평소 기준"으로 이동할 수 있다.
- **데이터 상태**: "기준정보 미등록"은 데이터 상태이지 건강 위험이 아니다.
- **권한**: 모든 조회·쓰기는 관리자 세션 + 세션 기관(다른 기관 문서·기준정보는 404/403, DB 함수도 기관·수급자 일치 확인).
  브라우저 키(anon·authenticated)에는 테이블·함수·버킷 권한이 없다.

### 화면

- 수급자 상세 "기준문서 · 기준정보": 원본 문서 목록(문서 기준일/미기재·업로드 시각·출처·파일·교체/철회 표시, 원본 보기·이 문서로
  기준정보 입력·교체본 올리기·철회), 문서 올리기(형식·용량 안내, 실패 시 입력 유지·같은 파일로 다시 올리기), 상충 상자(참고값 선택),
  종류별 기준정보(상태·버전·이전 버전·근거·확인·고치기·철회). 타임라인의 항목 태그는 "항목별 근거 연결 전" 표시와 보고 전체 열기.
- 조치 상세 "근거 기준정보(선택)": 연결 당시 버전·근거 문서·원본 보기·이후 수정 여부, 연결·해제(이유), 이력.
- 4단계 DB 준비 전(3단계까지 적용): 두 섹션 "준비 중", 저장 버튼 없음(서버도 503). 원본 버킷만 없으면 올리기만 "준비 중"이고
  관리자 입력 기준정보는 쓸 수 있다. 데모: `?demo=1&demo_workflow=stage3`.

### 이번 단계에서 하지 않은 것 · 한계

- 파일은 4MB까지다(Vercel 서버 함수 요청 한도 4.5MB 안에서 서버가 직접 검사·저장하기 위함). 더 큰 스캔본은 압축·분할이 필요하다.
- OCR·LLM 자동 추출 없음 — 관리자가 원본을 보고 입력한다.
- 잘못 올린 문서는 철회만 한다(원본 파일은 보존). 다른 수급자의 문서를 잘못 올린 경우 물리 삭제가 필요하면 사용자가 별도로 결정·실행해야 한다.
- 데모 모드는 원본을 이 브라우저 저장공간에만 두어 1MB까지만 받는다.
- 운영 Supabase(버킷 생성·파일 올리기·내려받기·PostgREST)에는 이 환경에서 접근할 수 없어 확인하지 못했다. SQL은 PGlite(실제 Postgres)로,
  화면 흐름은 데모 e2e로 검증했다.

   여러 번 실행해도 안전하다. 이 파일이 비공개 버킷 `care-source-documents`도 만든다.
3. 머리말의 확인 쿼리로 6개 값이 모두 true인지 본다(마지막 값 = 버킷이 비공개로 존재).
4. 관리자 화면을 새로고침하면 "준비 중"이 사라진다(앱 재배포 불필요). 실제 확인은 시험용 수급자·시험 파일로 먼저 해 보길 권한다.

## 8. 5단계 — 관찰 달력 · 원문 근거 · 반복 보고 후보 · 비교 가능한 값 차이 (2026-09-15)

PSST 대응: "여러 날 보고를 사람이 대조해야 하는 부담" → 수급자의 시간별 관찰과 변화 근거를 한 화면에서 찾고, 반복 보고와
저장된 값 차이를 관리자 판단·기존 조치로 잇는다. 진단·중증도·예측·점수는 만들지 않는다.

### 착수 시 확인

| 항목 | 판정 | 근거 |
|---|---|---|
| 기존 관찰 화면 | 있음(1단계) — 수급자 상세 타임라인의 "항목별 상태" 칩 | `storedObservations`(shared/recipientHub.ts)를 달력에서도 그대로 재사용 |
| 항목별 상태 저장 | **현장 흐름이 저장하지 않음** | 서버는 `observedDomains` 등을 받으면 저장하지만 `CareApp`은 한 번도 보낸 적이 없다(git 이력 확인). 1단계 때 "별도 결정"으로 남긴 것과 같다 |
| 관찰일·관찰 시각 | 없음 | 보고일(`report_date`, 한국 날짜)·제출 시각만 있다 |
| 보고 전체 상태 | 있음 | `initial_status_choice`(평소와 다름/비슷함/확인 필요) — 항목별 상태와 별개로 한 줄에 따로 보인다 |
| 수치 관찰값 | 보고에는 없음 | 값 비교는 4단계 기준정보(정식 척도)에서만 가능 |

**그래서 운영 데이터에서는 달력 대부분이 "항목 저장 없음"으로 보이고 반복 보고 후보는 거의 생기지 않는다.** 이 단계는 저장된 값을
있는 그대로 보여주는 틀과 규칙을 만든 것이며, 현장 흐름이 항목별 상태를 저장하게 할지는 사용자 결정이 필요한 별도 과제다.

### 관찰 달력(수급자 상세)

- 7일·30일(한국 날짜, 오늘 포함). 날짜는 **보고일 기준**이고 그 사실을 화면에 적는다. 관찰일 기준 표시는 하지 않는다(섞지 않음).
- 줄 = 세부 키(식사·수분, 이동, 낙상, 배설 …). 식사·활동·안전·신체·인지·정서·기타는 화면 묶음일 뿐. 과거 복합 키(식사·수분, 이동·낙상)는
  분해하지 않고 기록이 있을 때만 따로 한 줄.
- 칸 = 평소와 같음 ○ / 변화 ▲ / 미관찰 － / 불확실 ? / 미언급 · / 여러 기록·상충 ◆ / 항목 저장 없음 □ / 보고 없음(빈칸). 문자와 기호를 함께 쓴다.
  "미언급"은 그날 항목별 상태를 저장한 보고는 있지만 이 항목이 없는 경우, "항목 저장 없음"은 그날 보고는 있지만 아무 항목도 저장되지 않은 경우.
- 같은 날 여러 보고·상충 기록은 칸에 건수(×3)와 함께 표시하고, 칸을 누르면 그날 보고 전부(제출 시각·보고자·보고 유형·보고 전체 상태·원문 발췌·
  저장된 항목 상태·반려 여부)가 펼쳐지고 "보고 전체 열기"로 원문으로 간다. 항목별 근거가 없으므로 "항목별 근거 연결 전 — 보고 전체가 근거".
- 점수·꺾은선·보간 없음(그래프 요소 자체가 없다).

### 반복 보고 후보(초기 운영 규칙 `repeat_changed` v1)

- 규칙: 같은 수급자·같은 세부 영역에 "변화"가 저장된 보고가 최근 7일(기준일 포함) 중 **서로 다른 날 2일 이상**. 같은 날 여러 보고는 하루.
  세부 영역·수급자를 섞지 않는다. 반려된 보고는 신호에서 빼고 뺀 건수를 보인다.
- 표시: "식사 변화가 2일 보고됨" + "같은 증상이 계속됐거나 나빠졌다는 뜻이 아닙니다". 후보 수·수급자 수·변화 신호 수를 따로 센다.
- 기준: 관찰일이 없어 **보고일 기준**으로만 계산한다. 관찰일 기준은 "관찰일이 기록된 보고 없음 — 계산 대상 0건 · 제외 N건"으로 따로 알린다.
- 후보 자체는 저장하지 않고 매번 같은 규칙으로 계산한다. 후보의 열쇠 = 규칙·버전·기준·수급자·세부 영역·에피소드 시작일(변화 보고일 간격이
  7일 미만으로 이어진 묶음의 첫날) — 날이 지나 창이 움직여도 같은 후보로 남는다. 반려된 보고도 열쇠 계산에는 넣어, 반려 뒤에도 같은 후보에
  판단이 남아 "재검토 필요"로 보이게 했다.
- 기관 첫 화면 카드 "반복 보고 후보"(서버 전체 집계) → `/admin/work/repeat` 전체 목록.

### 비교 가능한 값 차이(`scale_value_diff` v1)

- 관리자 확인된 현재 버전의 정식 척도 결과끼리, 도구명·버전·단위가 같고 측정일이 다르며 값이 다를 때만. 같은 값이면 후보 없음.
- 비교하지 않는 것(이유별 건수 공개): 계획·목표, 관리자 메모, 초안·철회·이전 버전, 측정일 없음, 같은 날 값 상충, 측정 맥락이 기록되지 않은
  일반 관찰 수치, 도구 버전·단위가 다른 값끼리.
- 표시: "MMSE-K 1989: 24점(2026-03-01) → 21점(2026-08-20)", 차이 −3점 — "수치 차이일 뿐 악화·호전 판단이 아님". 보고자의 "평소와 다름"
  진술(반복 보고)과 섹션을 나눈다.

### 관리자 판단(후보와 분리 — 추가형 마이그레이션 `db/migrations/2026-09-18-change-candidate-reviews.sql`)

- 판단 4종: 변화 확인 / 평소 범위 / 추가 확인 필요 / 비교 부적절 + 근거(필수) + 선택적으로 **같은 수급자의 초안·진행 중 조치에 연결**.
  열린 조치를 후보 옆에 보여 중복 조치를 줄이고, 새 조치가 필요하면 기존 흐름(근거 보고 → 조치 만들기)을 쓴다. 자동으로 조치·요청을 만들지 않는다.
- 판단은 판단 당시 근거 스냅샷(보고 id·날짜 / 기준정보 id·버전)과 함께 쌓이고 수정·삭제되지 않는다. 같은 요청 재전송은 한 번만.
  서버는 후보를 다시 계산해 열쇠가 맞을 때만 받는다(화면이 보낸 근거를 믿지 않음).
- 판단 뒤 새 근거가 오면 "판단 뒤 새 근거 N건"을 보이되 판단을 바꾸지 않는다. 근거 보고가 반려·삭제되거나 기준정보가 철회·새 버전이 되면
  "재검토 필요"로 표시한다(판단 이력은 그대로). 더 이상 조건을 채우지 않는 후보의 판단은 "다시 볼 후보 판단" 목록에 남는다.
- 조치 상세에 "연결된 변화 후보 판단"이 보인다 → 후보 → 판단 → 기존 조치 → 현장 요청(3단계) 흐름이 이어진다.

### 이번 단계에서 하지 않은 것 · 한계

- 현장 흐름이 항목별 상태를 저장하지 않아 운영 데이터로는 달력·후보가 거의 비어 있다(위). 현장 저장을 켜는 일은 현장 화면·연구 지표에 영향이 있어
  사용자 결정 후 별도 과제로 남긴다.
- 관찰일·관찰 시각 입력은 만들지 않았다(보고일 기준만).
- 반복 규칙은 초기 운영 규칙 v1이다 — 임상적으로 검증된 기준이 아니며, 바꿀 때는 버전을 올린다(과거 판단은 이전 버전 열쇠로 남는다).

### DB 적용 절차(사용자 작업 — 이 환경에는 Supabase 접근 권한이 없음)

1. 2단계(§5) → 3단계(§6) → 4단계(§7) 파일을 먼저 적용한다.
2. SQL Editor → `db/migrations/2026-09-18-change-candidate-reviews.sql` → Run. 4단계가 없으면 멈추고 아무것도 바꾸지 않는다. 여러 번 실행해도 안전.
3. 머리말의 확인 쿼리 2개 값이 모두 true인지 본다. 적용 전에도 달력·후보 계산은 보이고, 후보 판단 저장만 "준비 중"이다.
